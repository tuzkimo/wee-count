# “一起记账 / WeeCount” 完整开发方案

## 1. 项目概述

* **项目名称**：一起记账（WeeCount）
* **定位**：一款**离线优先、安全纯净、支持家庭/团队协同**的资产级记账 App。
* **目标平台**：移动端优先（基于 Android 平台，后期可无缝复用到 iOS）。
* **设计原则**：
  * **离线优先 (Offline-First)**：断网状态下功能 100% 可用，网络恢复后无感异步同步。
  * **家庭协同 (Team Sync)**：以“账本（Ledger）”为权限边界，通过邀请码轻松组建家庭/团队，共享账目。
  * **极速记账 (Fast UX)**：自定义实体感数字键盘，支持多标签极速输入、智能联想、不产生页面遮挡。
  * **资产安全**：支持多账户间转账（如跨成员转账）、本地指纹锁保护、本地数据库（SQLite）加密存储。

## 3. 系统架构与数据流向

### 3.1 离线优先数据流

```text
[用户输入交易/转账]
       │
       ▼
[Svelte 5 状态变更] ──(触发)──► [本地 Haptics 振动]
       │
       ▼
[写入本地 SQLite (生成 UUID)]
       │
       ├──────────────────────────────────┐
       ▼ (在线状态)                       ▼ (离线状态)
[发起增量 Sync 接口]                [暂存本地，等待网络连接]
       │                                  │
       ▼                                  ▼
[写入云端 PostgreSQL]               [检测到网络恢复，触发同步]
```

### 3.2 权限控制边界：多账本模型

用户不直接隶属于某个家庭账本。系统通过“账本 (Ledger)”来进行数据隔离。一个用户可以同时拥有和切换多个账本：

1. **个人独立账本**：仅绑定当前 `user_id`，仅存在本地与云端自己的账户中。
2. **家庭/团队账本**：关联一个 `team_id`，凡是属于该 `team_members` 的用户，在同步时都会拉取该账本下的所有数据，实现多人协同。

## 4. 数据库设计 (双端结构对齐)

本地 SQLite 与云端 PostgreSQL 保持一致的结构体系，均使用 **UUID** 作为记录主键。

```sql
-- 1. 用户表 (云端存全量，本地仅缓存协同成员的信息)
CREATE TABLE users (
    id UUID PRIMARY KEY,
    nickname VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL, -- 密码哈希 (本地 SQLite 可留空或不存)
    avatar_url VARCHAR(255),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

-- 2. 团队表 (家庭)
CREATE TABLE teams (
    id UUID PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    created_by UUID REFERENCES users(id),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

-- 3. 团队成员关联表
CREATE TABLE team_members (
    team_id UUID REFERENCES teams(id),
    user_id UUID REFERENCES users(id),
    role VARCHAR(20) DEFAULT 'member', -- owner, member
    joined_at TIMESTAMP NOT NULL,
    PRIMARY KEY (team_id, user_id)
);

-- 4. 账本表
CREATE TABLE ledgers (
    id UUID PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    type VARCHAR(20) NOT NULL, -- 'personal', 'team'
    team_id UUID NULL REFERENCES teams(id),
    owner_id UUID REFERENCES users(id),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE
);

-- 5. 账户资产表 (计算余额制，防同步冲突)
CREATE TABLE accounts (
    id UUID PRIMARY KEY,
    ledger_id UUID REFERENCES ledgers(id) NOT NULL,
    owner_id UUID REFERENCES users(id) NOT NULL, -- 账户归属人
    name VARCHAR(100) NOT NULL, -- 如 "爸爸的招商卡", "妈妈的微信"
    type VARCHAR(50) NOT NULL, -- 'bank' (银行卡), 'credit_card' (信用卡), 'digital' (微信支付宝), 'debt' (花呗)
    initial_balance DECIMAL(12, 2) NOT NULL DEFAULT 0.00, -- 初始余额，当前余额为动态计算
    color VARCHAR(20),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE
);

-- 6. 分类表
CREATE TABLE categories (
    id UUID PRIMARY KEY,
    ledger_id UUID REFERENCES ledgers(id), -- NULL 为系统默认分类
    name VARCHAR(50) NOT NULL,
    type VARCHAR(20) NOT NULL, -- 'income', 'expense'
    icon VARCHAR(50),
    updated_at TIMESTAMP NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE
);

-- 7. 交易明细表 (支持转账)
CREATE TABLE transactions (
    id UUID PRIMARY KEY,
    ledger_id UUID REFERENCES ledgers(id) NOT NULL,
    user_id UUID REFERENCES users(id) NOT NULL, -- 操作记录人
    amount DECIMAL(12, 2) NOT NULL,
    type VARCHAR(20) NOT NULL, -- 'income', 'expense', 'transfer'

    -- 多账户核心设计
    from_account_id UUID REFERENCES accounts(id) NULL, -- 支出账户/转出账户
    to_account_id UUID REFERENCES accounts(id) NULL, -- 收入账户/转入账户

    category_id UUID REFERENCES categories(id) NULL, -- 转账时可为空
    occurred_at TIMESTAMP NOT NULL, -- 交易实际发生时间
    description TEXT,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE
);

-- 8. 标签定义表
CREATE TABLE tags (
    id UUID PRIMARY KEY,
    ledger_id UUID REFERENCES ledgers(id) NOT NULL,
    name VARCHAR(50) NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE,
    UNIQUE(ledger_id, name)
);

-- 9. 交易-标签关联表 (本地/云端实体多对多关联)
CREATE TABLE transaction_tags (
    transaction_id UUID REFERENCES transactions(id) ON DELETE CASCADE,
    tag_id UUID REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (transaction_id, tag_id)
);
```

## 5. 核心特色功能深度设计

### 5.1 团队组建与邀请工作流

为了保证不写复杂安卓代码实现扫码加入或直接搜索，系统采用**高时效随机邀请码**方案。

```text
成员 A (创建者)                  云端 Go 后端 + Redis               成员 B (加入者)
     │                                │                                 │
     ├─► 1. 创建团队并申请邀请码 ─────►│                                 │
     │                                ├──► 2. 生成 6 位码 (e.g. 583920)  │
     │                                │      写入 Redis (Expire: 24h)   │
     │◄─ 3. 返回邀请码及团队 ID ──────┤                                 │
     │                                │                                 │
     │ - - 通过微信复制发送给 B - - - - - - - - - - - - - - - - - - - - - -►│
     │                                │                                 │
     │                                │◄─ 4. 输入邀请码 583920 ─────────┤
     │                                ├──► 5. 校验通过，写入 Postgres    │
     │                                │      建立 team_members 关联     │
     │                                ├──► 6. 返回团队关联的 ledger_ids   │
     │                                ├────────────────────────────────►│
     │                                │ (B 触发同步，拉取该团队账本历史账单)
```

### 5.2 账户增量计算与转账设计

1. **规避同步冲突的余额算法**：
   由于多端离线修改同一账户会产生冲突，本地与云端均**不维护**一个强状态的 `balance` 字段。所有账户的当前余额均由 SQL 聚合计算得出：
   
   ```sql
   SELECT 
       a.id,
       a.name,
       (a.initial_balance 
        + COALESCE((SELECT SUM(amount) FROM transactions WHERE to_account_id = a.id AND is_deleted = false), 0)
        - COALESCE((SELECT SUM(amount) FROM transactions WHERE from_account_id = a.id AND is_deleted = false), 0)
       ) AS current_balance
   FROM accounts a
   WHERE a.id = ? AND a.is_deleted = false;
   ```
2. **转账处理**：
   当“爸爸转账给妈妈”时，前台写入一条 `type = 'transfer'` 的记录，`from_account_id = 爸爸的银行卡`，`to_account_id = 妈妈的微信`。这样，计算余额时，爸爸的账户动态减少对应金额，妈妈的账户动态增加对应金额，数学上始终保持一致性。

### 5.3 多标签输入与极速联想

* **交互逻辑**：
  1. 当用户进入记账页面，前端从本地 SQLite 载入最常用的前 15 个标签。
  2. 用户输入字符时（例如输入 `z`），Svelte 5 动态推导联想词，推荐带有 “z” 或拼音首字母匹配的标签（如 “早餐”、“纸巾”）。
  3. 用户在键盘上输入新标签并回车，前台自动调用 `create_local_tag` 存储进 SQLite，并绑定到当前交易上。
* **同步优化（扁平嵌套传输）**：
  为了不设计繁琐的 `transaction_tags` 中间表同步逻辑，`/sync` 接口传输时直接将关联标签嵌套在 Transaction 对象内部：
  
  ```json
  { "id": "trans-uuid-1", "amount": 12.0, "tag_ids": ["tag-uuid-1", "tag-uuid-2"] }
  ```
  
  云端 Go 接收后在事务中：`DELETE FROM transaction_tags WHERE transaction_id = 'trans-uuid-1'`，再批量插入新的关联关系。

### 5.4 原生振动自定义数字键盘

为了在手机端快速输入金额，我们不调起系统键盘。

* **实现方式**：
  
  1. 使用 CSS Grid 绘制一个 4x4 的美观数字键盘悬浮在页面底部。
  
  2. 每个按键绑定点击事件，通过 Tauri 原生插件触发微小、利落的物理振动：
     
     ```typescript
     import { vibrate } from '@tauri-apps/plugin-haptics';
     
     function handleKey(key: string) {
         // 触发 10 毫秒的安卓底层触觉振动
         vibrate(10); 
         // 键盘逻辑处理...
     }
     ```
  
  3. 这样不仅防止了页面被键盘顶起，还让记账具备了像计算器一样的实体按压感。

## 6. 云端接口 (API) 设计

后端基于 Go 编写，所有涉及账单和同步的数据接口均需在 Header 中携带 `Authorization: Bearer <JWT_TOKEN>`。

### 6.1 登录与注册

* `POST /api/v1/auth/register` (用户注册)
  * *输入*：`{ "email": "dad@example.com", "password": "xxx", "nickname": "爸爸" }`
  * *处理*：Bcrypt 加密密码存储。同时系统自动为该用户创建一个个人账本 `ledgers` 以及默认的账户类型（如微信支付、支付宝、现金钱包）。
* `POST /api/v1/auth/login` (用户登录)
  * *输入*：`{ "email": "dad@example.com", "password": "xxx" }`
  * *返回*：`{ "access_token": "jwt_xxx", "refresh_token": "jwt_yyy", "user": { ... } }`

### 6.2 团队管理

* `POST /api/v1/teams/create` (创建家庭)
  * *输入*：`{ "name": "史密斯家庭" }`
  * *返回*：`{ "team_id": "xxx", "shared_ledger_id": "yyy" }`
* `POST /api/v1/teams/invite` (申请邀请码)
  * *输入*：`{ "team_id": "xxx" }`
  * *处理*：在 Redis 写入哈希 `team_invite:583920` -> `team_id:xxx`，生存时间 24 小时。
  * *返回*：`{ "invite_code": "583920" }`
* `POST /api/v1/teams/join` (通过邀请码加入)
  * *输入*：`{ "invite_code": "583920" }`
  * *处理*：通过 Redis 校验并获取 `team_id`，在 `team_members` 中插入新关联。

### 6.3 离线优先的核心同步接口 (Sync)

* `POST /api/v1/sync` (双向增量同步)
  * *请求*：
    
    ```json
    {
      "last_synced_at": "2026-06-01T12:00:00Z",
      "local_changes": {
        "ledgers": [],
        "accounts": [],
        "tags": [],
        "transactions": [
          { "id": "t-1", "amount": 100.00, "tag_ids": ["tag-1"], "updated_at": "2026-06-02T08:00:00Z" }
        ]
      }
    }
    ```
  * *后端逻辑*：
    1. **写入本地变更**：遍历 `local_changes`。校验每个实体所属的账本是否确实归属该用户。执行 `UPSERT` 写入 PostgreSQL。若遇到冲突，根据 `updated_at` 执行最后写入者赢得冲突（LWW）策略。
    2. **拉取云端变更**：检索该用户有权访问的所有账本中，`updated_at > last_synced_at` 的所有更新记录（包括其他家庭成员写入的数据以及软删除数据）。
  * *返回*：
    
    ```json
    {
      "server_time": "2026-06-02T11:00:00Z", // 作为客户端下次同步的 last_synced_at
      "remote_changes": {
        "accounts": [],
        "tags": [{ "id": "tag-2", "name": "晚餐", "updated_at": "..." }],
        "transactions": [{ "id": "t-2", "user_id": "mom-id", "amount": 45.0, "tag_ids": ["tag-2"] }]
      }
    }
    ```

## 7. 客户端安全架构与指纹解锁

1. **数据沙盒与 Token 保护**：
   客户端启动时，Tauri 2.0 的 `LazyStore` 从 Android 底层加密存储文件中加载用户的 JWT [1.2.3]。

2. **指纹拦截保护**：
   在 App 开启“指纹密码”的情况下，切换到前台或启动时，Svelte 5 渲染一个全屏高斯模糊遮罩，阻断任何交互，同时 Tauri 调用安卓底层生物识别系统：
   
   ```typescript
   import { authenticate } from '@tauri-apps/plugin-biometric';
   
   async function checkLock() {
       const success = await authenticate({
           reason: '请验证指纹以进入“一起记账”'
       });
       if (success) {
           isAppLocked = false; // 移除全屏遮罩
       }
   }
   ```

该架构方案将复杂的同步冲突降到了最低，最大化地利用了 Svelte 5 在移动 WebView 下的渲染优势和 Tauri 2.0 的系统级安全沙盒 [1.2.1, 1.2.3]。这能让您用最干净的代码，交付出一款高质感、高可靠性的多端协同记账产品。
