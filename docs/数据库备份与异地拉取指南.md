# 数据库备份与 NAS 异地拉取指南

> 适用对象：没有运维经验也能照着操作。本文教你在云服务器上每天自动备份数据库（滚动保留最近 7 天），再让家里的 NAS 每天把备份拉回本地留一份。
>
> 需要你替换的只有下面几个值（其余路径都有默认值，跟着抄就能跑；想改看 1.3 和 2.4）：
> - `<用户名>`：服务器上 SSH 登录用的用户名
> - `<服务器内网地址>`：服务器在 EasyTier 里的虚拟 IP
> - `<SSH端口>`：SSH 端口，默认 22（**不是 22 才需要替**，见 2.2、2.4）

## 0. 最终效果

```text
云服务器（每天 03:30）                    NAS（每天 04:30）
┌──────────────────────────┐             ┌──────────────────────────┐
│ 1. pg_dump 导出数据库     │             │ 1. rsync 从服务器拉文件   │
│ 2. 存成 .sql.gz           │  EasyTier   │ 2. 存到本地目录           │
│ 3. 删掉 7 天前的旧备份    │◄─── VPN ────│ 3. 删掉 30 天前的旧备份   │
└──────────────────────────┘             └──────────────────────────┘
     保留最近 7 天                            保留最近 30 天
```

两边各自滚动清理，**服务器只留 7 天（省磁盘），NAS 留 30 天（要留久一点）**。就算服务器被人删了库，NAS 上还有 30 天内的副本。

用到的两个脚本都在本仓库里，改一次两边都能用：

| 脚本 | 放哪 |
|------|------|
| `scripts/backup-db.sh` | 云服务器（仓库里就有，跟着 `git pull` 更新） |
| `scripts/nas-pull-backup.sh` | NAS 上（NAS 没有仓库，手动装一份，见 2.4） |

## 1. 服务器侧：每天自动备份

> 以下命令都在**云服务器**上执行（SSH 登录后），用运行部署的那同一个账号。

### 1.1 把脚本取下来

仓库里的脚本随 `git pull` 一起来。项目目录按你实际部署的位置（下例假设在 `~/wee-count`）：

```bash
cd ~/wee-count && git pull
chmod +x scripts/backup-db.sh        # 万一提示 Permission denied 就执行这句
mkdir -p ~/backup                    # 放日志，脚本第一次跑也会自己建备份子目录
sudo apt update && sudo apt install -y rsync   # 推荐装（Debian/Ubuntu 系）：rsync 拉取需要两端都有 rsync
```

> 脚本放在仓库根的 `scripts/`（不在 `backend/`）是故意的：`backend/**` 一改动就会触发 GitHub 重新构建并部署后端，改个运维脚本不该顺带重启生产。
>
> 脚本顶部有「可调参数」几行，默认值直接能用，先不用管。
>
> **服务器没装 `rsync` 也不会挂**：2.4 的脚本会自动改用 `tar`（两端系统自带）把备份取回来，代价是每次全量重传。想省流量就在服务器上装一下 rsync（就是上面那行）。

`backup-db.sh` 干的事（就这四步）：

1. 在 `docker compose` 的 `postgres` 容器里跑 `pg_dump`，导成 `.sql.gz`；
2. 先写临时文件、自检通过（压缩包完整 + 里面确实是 pg_dump 输出）才改正式名字；
3. 文件名带日期，同一天重跑直接覆盖，不堆积；
4. 删掉 7 天前的旧备份。任何一步失败都会留下明确报错、不产生坏备份。

### 1.2 手动跑一次，确认能用

```bash
~/wee-count/scripts/backup-db.sh
```

期望输出（最后一行有日期和文件大小就对了）：

```text
2026-01-01 03:30:12 OK /home/<用户名>/backup/wee-count/wee-count-2026-01-01.sql.gz 1.2M
```

再确认文件不是空壳：

```bash
ls -lh ~/backup/wee-count/
zcat ~/backup/wee-count/wee-count-*.sql.gz | head -5
```

`head -5` 应该看到 `-- PostgreSQL database dump` 之类的 SQL 注释。**如果文件只有几十字节，或者这里报错，先别往下做**，把报错贴出来。

### 1.3 要改参数？改脚本顶部那几行（默认可直接跳过）

默认值就是本文用的这套（备份到 `~/backup/wee-count`、留 7 天），**不用改**。想改的话，用编辑器打开脚本，改最上面那一段：

```bash
nano ~/wee-count/scripts/backup-db.sh
# 改完按 Ctrl+O 回车保存，Ctrl+X 退出
```

```bash
# ====== 可调参数 ======
COMPOSE_DIR=$(cd "$(dirname "$0")/.." && pwd)/backend   # 后端目录；脚本放在仓库的 scripts/ 里就不用改
BACKUP_DIR=$HOME/backup/wee-count   # 备份存哪
KEEP_DAYS=7                         # 保留最近几天
PG_SERVICE=postgres                 # docker-compose.yml 里的数据库服务名
# =====================
```

> 这个文件是 git 管理的。改过之后，下次 `git pull` 如果恰好也改了这个文件会提示冲突；碰到就执行 `git checkout -- scripts/backup-db.sh` 放弃本地改动（git pull 完再改一遍），或干脆把脚本复制到仓库外面用（复制出去的话，把 `COMPOSE_DIR` 改成指向仓库里的 `backend` 目录）。
>
> 改了 `BACKUP_DIR` 的话，**2.4 里 NAS 脚本顶部的 `REMOTE_DIR` 也要跟着改**（填服务器上家目录的相对路径，或直接填绝对路径）。

### 1.4 交给 cron 每天自动跑

```bash
crontab -e
```

第一次会让你选编辑器，选 `nano`（数字最小的那个）最简单。在文件末尾加一行：

```cron
30 3 * * * $HOME/wee-count/scripts/backup-db.sh >> $HOME/backup/backup.log 2>&1
```

保存退出（nano：`Ctrl+O` 回车，再 `Ctrl+X`）。

- `30 3 * * *` 意思是每天凌晨 3:30（按**服务器所在时区**算）。
- 后面那串表示把每次运行的输出追加写进 `~/backup/backup.log`，出问题时有据可查。

确认写进去了：

```bash
crontab -l
```

第二天再看一眼日志和目录，两条都正常就说明自动备份跑通了：

```bash
tail -5 ~/backup/backup.log
ls -lt ~/backup/wee-count/ | head
```

## 2. NAS 侧：每天把备份拉回家里

> 以下命令在 **NAS** 上执行（SSH 登录你的 Debian NAS）。
> 先装齐要用的几个命令（已经有了会提示 already installed，可以忽略）：
> ```bash
> sudo apt update && sudo apt install -y rsync openssh-client cron
> ```

### 2.1 先确认两台机器真的通

在 NAS 上 ping 服务器的 EasyTier 地址（EasyTier 的虚拟 IP 通常是 `10.126.x.x` 这类，在服务器上执行 `easytier-cli peer` 能看到）：

```bash
ping -c 3 <服务器内网地址>   # 报 command not found 就先 sudo apt install -y iputils-ping
```

通不了就先解决 VPN 的事，后面所有步骤都会失败。

### 2.2 给 NAS 配一把钥匙（免密码登录）

NAS 要能自动登录服务器，用的是「公钥」而不是密码。下面的定时任务用 root 跑，所以钥匙就放在 root 家目录里：

```bash
sudo mkdir -p /root/.ssh && sudo chmod 700 /root/.ssh
sudo ssh-keygen -t ed25519 -f /root/.ssh/wee_count_pull -N ''
sudo cat /root/.ssh/wee_count_pull.pub
```

把最后一条命令输出的**一整行**复制下来（`ssh-ed25519 AAAA...` 开头），然后回到**服务器**上执行（把粘贴的内容替换掉 `<刚复制的那一行>`）：

```bash
echo '<刚复制的那一行>' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

回 NAS 测试免密登录（**不应该再问密码**）：

```bash
sudo ssh -p <SSH端口> -i /root/.ssh/wee_count_pull <用户名>@<服务器内网地址> 'ls -lt ~/backup/wee-count | head -3'
```

能看到备份文件名就成功了。第一次会问 `Are you sure you want to continue connecting?`，输入 `yes`。

> **SSH 不是 22 端口的话**，`-p <SSH端口>` 不能省（默认 22 可以写成 `-p 22` 也可以删掉）。这个端口等会要填到 2.4 脚本的 `SSH_PORT` 里，两处必须一致。

> 这一次测试不能省：它会把服务器的指纹记进 `/root/.ssh/known_hosts`。脚本里带了 `-o BatchMode=yes`（不问密码、不交互），指纹没记录过的话自动化会直接失败。用 `-o BatchMode` 是为了让「要输密码」这类情况立即报错，而不是挂着等输入把 cron 卡死。

### 2.3 建备份目录（必须在数据盘上）

先定好备份存哪个目录。**本文统一用 `/srv/backup/wee-count` 演示，跟着抄最省事**。你的数据盘若挂在别的地方（比如 `/mnt/data`），就把它换成 `/mnt/data/backup/wee-count`，并且：目录建在数据盘上、2.4 的配置里填这个路径、2.6 的 cron 里脚本路径不用动。

```bash
sudo mkdir -p /srv/backup/wee-count
df -h /srv/backup/wee-count
```

> ⚠️ `df` 输出的 `Mounted on` 一列必须指向你的**数据盘**。如果显示 `/`（根分区），说明这个目录还在系统盘上，换成数据盘的路径再来——否则数据盘没挂载时，备份会静默写到系统盘把系统盘写满（脚本里那个 `[ -d ... ]` 检查就是防这个）。

### 2.4 装脚本 + 改顶部几行

脚本内容和仓库里的 `scripts/nas-pull-backup.sh` 一致（改过记得两边同步）。先装到系统目录：

```bash
sudo tee /usr/local/bin/wee-count-pull-backup.sh > /dev/null <<'EOF'
#!/bin/sh
# 从服务器把 backup-db.sh 产出的备份拉到本机（NAS），滚动保留最近 N 天。
# 服务器和本机之间走内网（EasyTier 等），本脚本用 SSH 公钥免密登录。
#
# 用法：sudo /usr/local/bin/wee-count-pull-backup.sh
# 装好后先改下面「必须改」的两行，其余默认值不用动。

set -eu

# ====== 必须改 ======
SERVER=user@10.0.0.1                 # 服务器的 SSH 登录名@EasyTier 地址
BACKUP_DIR=/srv/backup/wee-count      # 备份存到本机哪个目录（必须是已挂载的数据盘目录）
# ====================

# ====== 按需改 ======
SSH_PORT=22                          # 服务器的 SSH 端口，不是 22 就改这里
TRANSFER=auto                        # 怎么把文件取回来：auto（推荐）/ rsync / tar
                                     # auto 会在两端都有 rsync 时用 rsync，否则自动改用 tar
# ====================

# ====== 一般不用改 ======
KEEP_DAYS=30                         # 本机保留最近几天
REMOTE_DIR=backup/wee-count          # 服务器上的备份位置，相对服务器的家目录；也可填绝对路径
SSH_KEY=/root/.ssh/wee_count_pull    # 本机登录服务器用的私钥
# =======================

if [ "$SERVER" = "user@10.0.0.1" ]; then
  echo "请先改脚本顶部的 SERVER（把 user@10.0.0.1 换成 用户名@服务器内网地址）" >&2
  exit 1
fi

# 目录必须已经存在：数据盘没挂载时直接失败，而不是悄悄把备份写到系统盘
[ -d "$BACKUP_DIR" ] || { echo "备份目录不存在，数据盘可能没挂载：$BACKUP_DIR" >&2; exit 1; }

ssh_q() {  # 带端口和密钥的 ssh；其余参数由调用处传进来
  ssh -p "$SSH_PORT" -i "$SSH_KEY" -o BatchMode=yes "$@"
}

if [ "$TRANSFER" = auto ]; then
  if command -v rsync > /dev/null 2>&1 && ssh_q "$SERVER" 'command -v rsync > /dev/null 2>&1'; then
    TRANSFER=rsync
  else
    TRANSFER=tar
  fi
fi
echo "$(date '+%F %T') 传输方式：$TRANSFER"

case "$TRANSFER" in
  rsync)
    # 故意不加 --delete：服务器只留自己那份天数，本机要留自己的份数
    rsync -az --no-perms --no-owner --no-group \
      -e "ssh -p $SSH_PORT -i $SSH_KEY -o BatchMode=yes" \
      "$SERVER:$REMOTE_DIR/" "$BACKUP_DIR/"
    ;;
  tar)
    # 退路：只用 ssh + tar（两端系统自带）。服务器没装 rsync 也能拉，代价是每次全量重传
    ssh_q "$SERVER" "tar -C '$REMOTE_DIR' -czf - ." | tar -xzf - -C "$BACKUP_DIR"
    ;;
  *)
    echo "TRANSFER 只能是 auto / rsync / tar，当前是：$TRANSFER" >&2
    exit 1
    ;;
esac

# 一份都没拉到就直接失败，不要打出「OK 本地共 0 份」这种假成功
if ! ls -1 "$BACKUP_DIR"/wee-count-*.sql.gz > /dev/null 2>&1; then
  echo "没拉到任何备份：确认服务器上已经跑过备份（backup-db.sh），且 REMOTE_DIR=$REMOTE_DIR 是对的" >&2
  exit 1
fi

find "$BACKUP_DIR" -name 'wee-count-*.sql.gz' -type f -mtime "+$((KEEP_DAYS-1))" -delete

echo "$(date '+%F %T') OK 本地共 $(ls -1 "$BACKUP_DIR" | wc -l) 份，最新：$(ls -t "$BACKUP_DIR" | head -1)"
EOF

sudo chmod +x /usr/local/bin/wee-count-pull-backup.sh
```

然后用编辑器改最上面那几行：

```bash
sudo nano /usr/local/bin/wee-count-pull-backup.sh
```

```sh
# ====== 必须改 ======
SERVER=<用户名>@<服务器内网地址>     # 服务器的 SSH 登录名@EasyTier 地址
BACKUP_DIR=/srv/backup/wee-count      # 2.3 里建的目录；建在别处就改成那个路径
# ====================

# ====== 按需改 ======
SSH_PORT=22                          # 服务器的 SSH 端口，不是 22 就改（同 2.2）
TRANSFER=auto                        # 一般不用动；auto = 两端有 rsync 就用 rsync，否则自动用 tar
# ====================
```

改完按 `Ctrl+O` 回车保存，`Ctrl+X` 退出。

> 忘了改 `SERVER` 的话，跑脚本会直接提醒你；`SSH_PORT` 填错会报 `Connection refused`（端口错）或 `Permission denied`（端口对了但密钥没配好）。

### 2.5 手动跑一次，确认能拉到

```bash
sudo /usr/local/bin/wee-count-pull-backup.sh
ls -lh /srv/backup/wee-count/
```

目录里出现和服务器上同名的 `wee-count-*.sql.gz` 就成功了。

### 2.6 加到定时任务

Debian 用 cron。先确认 cron 在跑：

```bash
sudo systemctl enable --now cron
systemctl status cron --no-pager | head -3
```

看到 `active (running)` 就对了。然后编辑 **root 的 crontab**：

```bash
sudo crontab -e
```

第一次会让你选编辑器，选 `nano`（数字最小的那个）。在文件末尾加一行：

```cron
30 4 * * * /usr/local/bin/wee-count-pull-backup.sh >> /var/log/wee-count-pull.log 2>&1
```

保存退出（nano：`Ctrl+O` 回车，再 `Ctrl+X`），确认写进去了：

```bash
sudo crontab -l
```

- `30 4 * * *` = 每天凌晨 4:30（比服务器备份晚 1.5 小时，留足时间；也按 NAS 自己的时区算）。
- 结尾那段重定向必须留着：cron 默认想把输出邮寄给用户，而家用 NAS 一般不装邮件服务，报错会被直接丢掉。日志写到 `/var/log/` 而不是跟着备份放，万一数据盘没挂上也不会悄悄写到系统盘里。
- 想手动试一次不用等到 4:30，直接 `sudo /usr/local/bin/wee-count-pull-backup.sh`，效果一样。

> cron 自己干活的痕迹在 `/var/log/syslog` 里：`grep CRON /var/log/syslog | tail -5`（Debian 12 及以后也可能在 `/var/log/cron.log`）。

### 2.7 （可选，更安全一点）

上面那把钥匙等于给了 NAS 一个能登录服务器的账号。如果 NAS 被人拿到，攻击者也能登上服务器。想收紧的话，在**服务器**的 `~/.ssh/authorized_keys` 里把 NAS 的那一行前面加上限制（路径要和服务器脚本里的 `BACKUP_DIR` 一致）：

```text
restrict,command="rsync --server --sender -logDtpre.iLsfxCIvu . /home/<用户名>/backup/wee-count/" ssh-ed25519 AAAA...那一行剩下的部分
```

这样这把钥匙只能用来拉备份目录，不能开 shell、不能端口转发。（SSH 端口改过也不影响这一行。）

两个注意点：

- 加了之后 2.2 里那个 `ssh ... 'ls -lt ...'` 测试命令就不能用了，改用跑脚本的方式验证。
- 不同 rsync 版本的 `command=` 字符串可能不一样。加完**先在 NAS 上手动跑一次拉取**，报错了就把 `command="..."` 去掉、只留 `restrict`（去掉 SSH 转发能力，仍能防一部分滥用）。

## 3. 日常：怎么确认它还活着

备份最危险的不是报错，而是**悄悄停了没人知道**。每周花 10 秒看一眼：

| 在哪台机器 | 命令 | 正常应该看到 |
|------------|------|--------------|
| 服务器 | `tail -3 ~/backup/backup.log` | 最新一行是今天的日期，带 `OK` |
| 服务器 | `ls -lt ~/backup/wee-count/ \| head -3` | 最新文件是今天的，共 7 个 |
| NAS | `sudo tail -3 /var/log/wee-count-pull.log` | 最新一行是今天的日期，带 `OK` |
| NAS | `ls -lt /srv/backup/wee-count/ \| head -3` | 最新文件是今天的 |

**如果服务器上有日志、NAS 上没有**：说明 VPN 或钥匙的问题，手动在 NAS 上跑一次脚本看报错（多半是 `ping` 不通或钥匙没配对）。

**如果两边日志都停在几天前**：检查 cron 是否还在（服务器/NAS 各自 `crontab -l`）、NAS 上 `systemctl status cron` 是否 active、以及服务器上 `docker compose ps` 数据库容器是否正常。

## 4. 真出事时怎么恢复

### 4.1 恢复线上数据库

> ⚠️ 这会把数据库恢复成备份那一刻的状态，**之后新产生的数据会丢**。只在确实需要回滚时做。
>
> **不要把备份直接灌进已经有数据的库**：那会报一堆 `already exists`，最后库里是「旧的+新的」混在一起，比恢复之前更难收拾。正确做法是先把库清空再灌。

在**服务器**上依次执行（`BACKUPS` 是服务器脚本里的备份目录；文件名换成你要恢复的那个）：

```bash
BACKUPS=$HOME/backup/wee-count
FILE=$BACKUPS/wee-count-2026-01-01.sql.gz
cd ~/wee-count/backend

# 1. 先停后端，避免恢复过程中还在写数据
docker compose stop api

# 2. 把「现在的状态」另存一份，万一恢复错了还能退回去
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' | gzip > /tmp/before-restore.sql.gz

# 3. 清空并重建数据库
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'

# 4. 灌入备份（ON_ERROR_STOP=1 表示碰到任何错误就立刻停，不会闷头跑出一个残缺的库）
gunzip -c "$FILE" | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# 5. 把后端起回来
docker compose start api
```

第 4 步唰唰输出一堆 `CREATE TABLE`、`COPY` 是正常的。报错了就别继续，把报错贴出来。

> 上面的命令不用管用户名和库名：它们直接取容器里的 `POSTGRES_USER` / `POSTGRES_DB`，你改过 `.env` 也照样对。

### 4.2 先演练一次（强烈建议）

备份到底能不能恢复，**没演练过就不算验证过**。演练不影响线上数据：起一个一次性的空数据库，把备份灌进去看看有没有数据。用的是服务器上已经有的镜像，不会额外下载东西。

```bash
LATEST=$(ls -t $HOME/backup/wee-count/wee-count-*.sql.gz | head -1)

docker run -d --name pg-drill -e POSTGRES_PASSWORD=drill -e POSTGRES_USER=wee -e POSTGRES_DB=wee-count postgres:16-alpine

# 等这个临时库真正启动（最多等 60 秒）
for i in $(seq 1 30); do docker exec pg-drill pg_isready -U wee > /dev/null 2>&1 && break; sleep 2; done

# 灌备份：没有报错、没有输出就是正常的
gunzip -c "$LATEST" | docker exec -i pg-drill psql -v ON_ERROR_STOP=1 -U wee -d wee-count > /dev/null
docker exec -i pg-drill psql -U wee -d wee-count -c 'select count(*) from users;'
docker exec -i pg-drill psql -U wee -d wee-count -c 'select count(*) from transactions;'

docker rm -f pg-drill   # 演练完删掉临时容器，不留垃圾
```

`count` 出来的数字接近你 App 里的用户数 / 账目数，就说明备份是**真的能恢复**的。建议每季度做一次。

> 演练里的 `wee` / `wee-count` 要和 `.env` 里的 `POSTGRES_USER` / `POSTGRES_DB` 一致。如果你改过这两个值，把上面两条 `-e` 和两条 `psql -U/-d` 一起改；否则 dump 里的对象属主找不到对应角色，第三步会报错停下。

## 5. 常见问题

**Q: 备份文件多大算正常？**
几百 KB 到几 MB 都正常。突然变成几十字节说明 dump 失败了，去翻日志。

**Q: 同一天跑了两次会怎样？**
文件名带日期，第二次直接覆盖第一次，不会堆积——这也是用日期命名而不是时间戳的原因。

**Q: 服务器磁盘被备份撑爆了？**
正常不会（7 份 × 几 MB）。真担心就把服务器脚本顶部的 `KEEP_DAYS` 改成 3。

**Q: NAS 上想留更久？**
同样改脚本顶部的 `KEEP_DAYS`（比如 `90`）。两台机器上的脚本各改各的，互不影响。

**Q: 服务器上没装 rsync 会怎样？**
脚本会自动改用 `tar` 传（两端系统自带），能用，只是每次把全部备份重传一遍。NAS 的日志（`/var/log/wee-count-pull.log`）里会写一行 `传输方式：tar`，看到就说明走的退路。想用 rsync 就在服务器上 `sudo apt install -y rsync`。

**Q: SSH 不是 22 端口？**
把脚本顶部的 `SSH_PORT` 改成实际端口（2.2 的手动测试命令也要带 `-p`）。忘了改的典型报错是 `Connection refused`。

**Q: 服务器 cron 日志里写 `docker: command not found`？**
cron 的 `PATH` 比登录 shell 小得多。在 crontab（服务器那份）顶部加一行 `PATH=/usr/local/bin:/usr/bin:/bin`，再重新跑一次即可。

**Q: 服务器 cron 日志里写 `permission denied`？**
脚本没有可执行权限（git 里没带上），`chmod +x ~/wee-count/scripts/backup-db.sh` 一下就行。

**Q: 能不能让 App 的本地数据也备到服务器？**
不在本文范围。客户端是离线优先的本地 SQLite，数据不出设备，这是设计约定。
